# Kế Hoạch Thiết Kế Kiến Trúc & Triển Khai - Phiên Bản V2 (gRPC & Kafka)

Hệ thống Đặt Vé Xe Khách (Bus Booking System) phiên bản **V1 (Modular Monolith)** đã hoàn thành xuất sắc các mục tiêu về an toàn giao dịch, kiểm soát đồng thời (Redis Lock) và đồng bộ thời gian thực (WebSocket). 

Tuy nhiên, để hệ thống đạt được khả năng mở rộng cao (High Scalability), khả năng chịu lỗi (Fault Tolerance) và tách biệt rõ ràng trách nhiệm giữa các cấu phần, chúng ta cần tiến tới phiên bản **V2 (Distributed Microservices/Decoupled Monolith)**.

Tài liệu này vạch ra kiến trúc V2, các ý tưởng thiết kế chi tiết sử dụng **gRPC** và **Kafka**, đồng thời cung cấp lộ trình thực hiện từng bước.

---

## 1. Tổng Quan Kiến Trúc V2 (System Architecture V2)

Kiến trúc V2 chuyển đổi cơ chế giao tiếp nội bộ từ **in-memory Go channels** và **gọi hàm trực tiếp (monolith calls)** sang:
1. **gRPC (HTTP/2):** Dành cho các giao tiếp **đồng bộ (Synchronous)**, yêu cầu độ trễ thấp và tính nhất quán tức thời (ví dụ: kiểm tra tồn tại của ghế, xác thực tài khoản).
2. **Apache Kafka:** Dành cho các giao tiếp **bất đồng bộ (Asynchronous)**, giúp xử lý các sự kiện quan trọng (như tạo booking, kết quả thanh toán, cập nhật trạng thái ghế) nhằm tăng độ bền vững dữ liệu, hỗ trợ retry/DLQ và khả năng scale-out của các consumer.

```mermaid
graph TD
    %% Clients
    Client([Web Client / Mobile Client]) -- HTTP/WS --> APIGateway[API Gateway / cmd/api]

    %% API Gateway to gRPC Services
    APIGateway -- gRPC --> BusService[Bus & Seat Inventory Service]
    APIGateway -- gRPC --> BookingService[Booking Service]
    APIGateway -- gRPC --> UserService[User Service]

    %% Kafka Broker
    subgraph Message Broker (Kafka)
        TopicBooking[Topic: booking-events]

    BookingService -- Publish booking.created --> TopicBooking
    TopicBooking -- Consume --> PaymentService[Payment Service / Worker]

    TopicPayment -- Consume --> NotificationService[Notification Service]

    %% Redis & Postgres
    BookingService --> DB_Booking[(Postgres: Bookings)]
    BookingService --> Redis_Lock[(Redis: Temp Lock)]
    BusService --> DB_Bus[(Postgres: Bus & Seats)]
    
    %% WebSocket integration
    TopicSeat -- Consume --> APIGateway
    APIGateway -- Broadcast "seat_locked/released" --> Client
```

## 2. Các Service Đề Xuất & Nhiệm Vụ (Proposed Microservices)

Để đơn giản hóa và tối ưu tài nguyên trong giai đoạn đầu, chúng ta có thể triển khai theo mô hình **Monorepo** với các file chạy độc lập (`cmd/api`, `cmd/booking-service`, `cmd/bus-service`, `cmd/payment-service`, `cmd/notification-service`).

| Service | Protocol | Nhiệm vụ chính |
| :--- | :--- | :--- |
| **API Gateway / WebSocket Hub** (`cmd/api`) | HTTP / WS | Nhận request từ Client, routing đến các gRPC service; Quản lý kết nối WS và consume Kafka topic `seat-events` để push cho user. |
| **Bus Service** (`cmd/bus-service`) | gRPC | Quản lý lộ trình, xe, ghế. Thực hiện khóa ghế tạm thời bằng Redis Lock. |
| **Booking Service** (`cmd/booking-service`) | gRPC & Kafka | Khởi tạo đơn đặt vé, xác nhận đơn hàng, quản lý trạng thái (`PENDING_PAYMENT`, `PAID`, `EXPIRED`, `FAILED`). |
| **Payment Service** (`cmd/payment-service`) | Kafka | Lắng nghe event từ Kafka để xử lý thanh toán bất đồng bộ qua các Cổng thanh toán (giả lập hoặc thật) và publish kết quả thanh toán. |
| **Notification Service** (`cmd/notification-service`) | Kafka | Lắng nghe kết quả thanh toán để gửi vé điện tử (Email/SMS) cho khách hàng. |

## 3. Ứng Dụng gRPC (Synchronous Communication)

### 3.1. Tại sao dùng gRPC?
* **Loại bỏ HTTP overhead:** Hoạt động trên HTTP/2, multiplexing, nén payload nhị phân (Protobuf) giúp tiết kiệm băng thông và tăng tốc độ xử lý.
* **Type Safety & Schema-driven:** Định nghĩa cấu trúc dữ liệu và API interface chặt chẽ trong file `.proto`, tự động sinh mã nguồn Go (tránh lỗi sai kiểu dữ liệu hoặc thiếu trường thông tin).

### 3.2. Thiết Kế Protobuf (`proto/`)

Chúng ta sẽ khởi tạo các định nghĩa service tại thư mục `proto/`:

#### A. `proto/bus.proto`
Định nghĩa việc truy vấn chuyến xe và giữ chỗ (Seat Locking):
```protobuf
syntax = "proto3";

package bus;
option go_package = "booking-system/proto/bus";

service BusInventoryService {
  rpc GetBusDetails (GetBusDetailsRequest) returns (GetBusDetailsResponse);
  rpc LockSeats (LockSeatsRequest) returns (LockSeatsResponse);
  rpc ReleaseSeats (ReleaseSeatsRequest) returns (ReleaseSeatsResponse);
  rpc CheckSeatsAvailable (CheckSeatsAvailableRequest) returns (CheckSeatsAvailableResponse);
}

message GetBusDetailsRequest {
  string bus_id = 1;
}

message SeatInfo {
  string seat_code = 1;
  string status = 2; // AVAILABLE, LOCKED, BOOKED
}

message GetBusDetailsResponse {
  string bus_id = 1;
  repeated SeatInfo seats = 2;
  double price = 3;
}

message LockSeatsRequest {
  string bus_id = 1;
  repeated string seat_codes = 2;
  string temp_user_id = 3;
}

message LockSeatsResponse {
  bool success = 1;
  string message = 2;
}

message ReleaseSeatsRequest {
  string bus_id = 1;
  repeated string seat_codes = 2;
}

message ReleaseSeatsResponse {
  bool success = 1;
}

message CheckSeatsAvailableRequest {
  string bus_id = 1;
  repeated string seat_codes = 2;
}

message CheckSeatsAvailableResponse {
  bool all_available = 1;
}
```

#### B. `proto/booking.proto`
Định nghĩa luồng đặt vé:
```protobuf
syntax = "proto3";

package booking;
option go_package = "booking-system/proto/booking";

service BookingService {
  rpc ConfirmBooking (ConfirmBookingRequest) returns (ConfirmBookingResponse);
}

message ConfirmBookingRequest {
  string bus_id = 1;
  repeated string seat_codes = 2;
  string user_name = 3;
  string email = 4;
  string phone = 5;
  string temp_user_id = 6;
}

message ConfirmBookingResponse {
  string booking_id = 1;
  double total_amount = 2;
  string status = 3;
}
```

## 4. Ứng Dụng Kafka (Asynchronous Event-Driven)

### 4.1. Tại sao dùng Kafka?
* **Khả năng chịu tải vượt trội (High Throughput):** Lưu trữ tuần tự trên ổ đĩa, xử lý hàng triệu message/giây.
* **Đảm bảo tính bền vững (Durability):** Ghi log sự kiện xuống đĩa, tránh mất mát dữ liệu khi hệ thống bị sập giữa chừng (vấn đề mà in-memory channel V1 gặp phải).
* **Scale ngang dễ dàng (Consumer Groups):** Cho phép chạy nhiều replica của Payment Worker hoặc Notification Worker mà không sợ xử lý trùng lặp nhờ cơ chế phân chia partition của Kafka.
* **Event Replay:** Khả năng phát lại các sự kiện để khắc phục sự cố hoặc phục vụ mục đích phân tích dữ liệu (Analytics).

### 4.2. Các Topics & Schema Sự Kiện

#### 1. Topic `booking-events` (Partition Key: `booking_id`)
* **Sự kiện:** `booking.created`
* **Producer:** `Booking Service` (bắn ra ngay sau khi write booking vào Database thành công ở trạng thái `PENDING_PAYMENT`).
* **Payload:**
  ```json
  {
    "event_id": "uuid-xxx",
    "event_type": "booking.created",
    "timestamp": "2026-07-06T18:30:00Z",
    "data": {
      "booking_id": "booking-uuid",
      "amount": 250000.0,
      "email": "user@example.com"
    }
  }
  ```

#### 2. Topic `payment-events` (Partition Key: `booking_id`)
* **Sự kiện:** `payment.succeeded` hoặc `payment.failed`
* **Producer:** `Payment Service` (bắn ra sau khi xử lý giao dịch với ngân hàng/cổng thanh toán).
* **Consumer:**
  * `Booking Service` lắng nghe để cập nhật trạng thái đơn hàng thành `PAID` hoặc `FAILED`, đồng thời cập nhật dữ liệu ghế sang `BOOKED` hoặc `AVAILABLE`.
  * `Notification Service` lắng nghe để gửi Email hóa đơn/vé hoặc thông báo thanh toán thất bại.
* **Payload:**
  ```json
  {
    "event_id": "uuid-yyy",
    "event_type": "payment.succeeded",
    "timestamp": "2026-07-06T18:31:00Z",
    "data": {
      "booking_id": "booking-uuid",
      "transaction_id": "tx-12345",
      "payment_method": "VNPAY"
    }
  }
  ```

#### 3. Topic `seat-events` (Partition Key: `bus_id`)
* **Sự kiện:** `seat.locked`, `seat.released`
* **Producer:** `Bus Service` (khi người dùng thao tác lock/unlock trên cache).
* **Consumer:** `API Gateway` (lọc sự kiện và forward qua các WebSocket connection tương ứng để cập nhật UI thời gian thực mà không cần API Gateway gọi trực tiếp WebSocket Hub in-memory). Điều này giúp API Gateway scale ngang thoải mái!

## 5. Giải Quyết Vấn Đề Lock Expiration & Độ Tin Cậy

### 5.1. Khuyết điểm của Redis Keyspace Notifications (V1)
Trong V1, chúng ta dựa vào sự kiện `expired` từ Redis để kích hoạt tiến trình tự động hủy vé quá hạn (15 phút).
> [!WARNING]
> **Redis Keyspace Notifications là cơ chế At-most-once (không đảm bảo phân phối).** 
> Nếu ứng dụng đang restart hoặc gặp sự cố mạng đúng lúc key hết hạn, sự kiện đó sẽ bị **mất vĩnh viễn**. Kết quả là vé sẽ bị kẹt ở trạng thái `PENDING_PAYMENT` và ghế sẽ bị khóa vô thời hạn.

### 5.2. Giải pháp cải tiến cho V2
1. **Sử dụng Redis Sorted Set (ZSet) làm Delay Queue:**
   * Khi tạo booking, thêm `booking_id` vào một Redis ZSet với điểm số (Score) = `UnixTimestamp lúc hết hạn (Now + 15m)`.
   * Một worker chạy nền sẽ chạy lệnh polling:
     ```redis
     ZRANGEBYSCORE expiration_queue -inf <current_timestamp> LIMIT 0 10
     ```
   * Sau khi xử lý hủy vé quá hạn thành công, xóa item ra khỏi ZSet. Cơ chế này đảm bảo không bao giờ bị sót sự kiện vì dữ liệu vẫn nằm đó cho đến khi được xóa chủ động.
2. **Transactional Outbox Pattern:**
   * Nhằm tránh việc ghi Database thành công nhưng bắn event sang Kafka thất bại (hoặc ngược lại - Dual Write Problem).
   * Tạo bảng `outbox` trong DB Postgres của `Booking Service`. Mọi thay đổi trạng thái booking và event tương ứng sẽ được lưu vào DB trong **cùng một transaction**.
   * Một **Outbox Worker** chuyên dụng (hoặc công cụ CDC như Debezium) sẽ đọc bảng này và đẩy sang Kafka một cách tin cậy (At-least-once).

## 6. Lộ Trình Triển Khai Từng Bước (Implementation Roadmap)

Để quá trình chuyển đổi mượt mà và không làm đứt gãy luồng công việc hiện tại, chúng ta có thể thực hiện theo các bước sau:

### Bước 1: Chuẩn Bị Hạ Tầng (Infrastructure Setup)
* Cập nhật `docker-compose.yml` bổ sung Kafka (chọn chế độ KRaft để không cần Zookeeper giúp chạy nhẹ hơn).
* Cài đặt thư viện client cho Kafka (ví dụ: `github.com/segmentio/kafka-go` hoặc `github.com/confluentinc/confluent-kafka-go`).
* Cài đặt công cụ grpc và protobuf: `grpc`, `protoc-gen-go`, `protoc-gen-go-grpc`.

### Bước 2: Định Nghĩa Hợp Đồng gRPC (Protobuf Setup)
* Tạo các file `.proto` trong thư mục `proto/` như đã phác thảo.
* Viết Makefile lệnh `make gen-proto` để tự động compile file proto sang Go code.

### Bước 3: Tách Biệt Service Nội Bộ (Internal Refactoring to gRPC)
* Chuyển các hàm logic trong Usecase của `Bus` và `Booking` thành các gRPC Service.
* Viết gRPC Server khởi chạy song song với HTTP server hiện tại.
* Dùng gRPC Client để API Gateway giao tiếp với các Service thay vì gọi trực tiếp package.

### Bước 4: Tích Hợp Kafka Cho Thanh Toán
* Đổi `event.PaymentEventBus` (in-memory channel) sang Kafka Client.
* Khi `ConfirmBooking` thành công, `Booking Service` bắn event lên Kafka topic `booking-events`.
* Phát triển `Payment Worker` chạy độc lập, consume topic `booking-events`, xử lý thanh toán, và đẩy kết quả về `payment-events`.
* `Booking Service` consume topic `payment-events` để update trạng thái DB.

### Bước 5: Cải Tiến Xử Lý Hết Hạn & WebSocket
* Thay thế Redis Keyevent Expired bằng cơ chế **ZSet Delay Queue** hoặc bổ sung một cron job kiểm tra quét DB (đảm bảo tính tin cậy tuyệt đối).
* Đưa WebSocket Event `seat_locked/released` lên Kafka topic `seat-events` để cho phép scale-out Gateway.

## 7. Bảng So Sánh V1 vs V2

| Đặc tính | Phiên bản V1 (Modular Monolith) | Phiên bản V2 (Distributed gRPC & Kafka) |
| :--- | :--- | :--- |
| **Giao tiếp Đồng bộ** | Gọi hàm nội bộ Go (In-memory func call) | gRPC (HTTP/2, Protobuf) |
| **Giao tiếp Bất đồng bộ** | Go Channels (Mất dữ liệu nếu sập app) | Apache Kafka (Bền vững, bền bỉ trên đĩa) |
| **Khả năng Mở rộng** | Giới hạn ở 1 instance duy nhất để giữ đồng bộ | Tách biệt các service để scale độc lập, hỗ trợ Consumer Groups |
| **Độ tin cậy xử lý quá hạn** | Phụ thuộc Redis Keyspace Expired (At-most-once) | Redis ZSet Delay Queue + Outbox Pattern (At-least-once) |
| **Scale WebSocket** | Khó khăn vì Hub nằm tại RAM của API Gateway | Dễ dàng vì các Gateway instance giao tiếp qua Kafka topic `seat-events` |
